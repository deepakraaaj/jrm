05 / Engineering playbook

How to minimize cost without lowering safety quality

01 · Offline geographic enrichment

Ingest schools, hospitals, POIs, route geometry and accident datasets on a schedule. Use indexed PostGIS lookups instead of charging for each nearby-place request.

high impact

02 · Cache by road tile / corridor

Weather/traffic snapshots are shared across vehicles. Refresh according to provider validity, severity and observed change—not at every GPS ping.

high impact

03 · One AI summary per assessment

LLM sees compact validated risk events, not raw points. Cache explanation by assessment version; avoid LLM calls for every position.

high impact

04 · Distinguish traffic flow vs routing

Traffic APIs may charge per tile, corridor, flow segment or query. Model provider-specific billing units rather than treating every hit as a single request.

verify contract

05 · Right-size event backbone

Kafka suits high-throughput replay/stream processing, but SQS or Redis Streams may reduce operations for smaller workloads. Choose by retention, throughput and failure recovery.

trade-off

06 · Fail safely

When a live API is down, use last-known-valid data only within its TTL, mark stale/missing coverage, and keep deterministic warnings operational.

reliability
Illustrative optimization: 52,000 journeys × 3 weather requests = 156,000 uncached requests/month. If 95% of those checks are served from a valid shared cache, ~7,800 requests reach the provider. The actual cache hit rate must be measured in production; it depends on route overlap, geography, refresh frequency, response terms and freshness requirements.
06 / The journey told as inputs and outputs

From latitude/longitude to response delivered to the driver

These JSON examples define proposed internal JRM contracts; they are not official vendor schemas. Adapters must map actual vendor responses into them.

Step 1 · User creates a route — inbound contract
{
  "routeId": "R-1001", "journeyDateTime": "2026-10-16T06:00:00+05:30",
  "vehicleType": "HEAVY_TRUCK",
  "source": {"lat": 13.0827, "lon": 80.2707},
  "destination": {"lat": 12.9716, "lon": 77.5946},
  "encodedPolyline": "<encoded-route-polyline>"
}

Source/destination alone are not enough for accurate segment-level JRM. Use a validated polyline or routing provider; determine the route date/time to align weather and events.

Step 2 · Existing FastAPI engine — geometry & POI input/output
INPUT: routeId + encodedPolyline + route time
LOOKUP: PostgreSQL locations; BallTree proximity; curvature rules
OUTPUT:
{
  "routeId":"R-1001",
  "segments":[{"segmentId":"S-001","riskType":"SHARP_CURVE","geometry":"...","baseRisk":0.7}],
  "pois":[{"type":"SCHOOL","lat":12.97,"lon":77.59}],
  "jrmPolyline":"..."
}
Step 3 · External API adapters — request/normalized output
Routing input: [origin, destination, waypoints, vehicle profile]
Routing output: [geometry, ETA, road class, restrictions (if supplied)]
Traffic input: [corridor geometry, time window]
Traffic output: [segment, speed, free-flow speed, closure, incident, validUntil]
Weather input: [route sample locations, expected passing timestamps]
Weather output: [precipitation, wind, visibility, alert severity, forecast validUntil]
Disaster input: [route bounding corridor, journey time]
Disaster output: [official alert area, event, severity, issuedAt, expiresAt]
Event input: [route stops/regions, dates]
Event output: [event type, venue/area, window, expected impact if evidenced]
Historic crash input: [route geometry, vehicle class, historical window]
Historic crash output: [blackspot segments, crash counts, data provenance]
POI input: [corridor, category, radius]
POI output: [name/type, location, provider ID, timestamp]

Every normalized output carries: source, fetchedAt, validUntil,
license/reference, spatial accuracy, provider status and missing-data flags.
Step 4 · Risk fusion + AI — verified assessments, not invented hazards
{
 "segmentId":"S-001",
 "signals":[{"source":"JRM_CURVATURE","type":"SHARP_CURVE"},
            {"source":"WEATHER","type":"HEAVY_RAIN","freshness":"VALID"}],
 "deterministicRiskScore":82,
 "riskLevel":"HIGH",
 "advisory":"Reduced traction may increase risk on this curve.",
 "verifiedFactsOnly":true,
 "modelVersion":"risk-v1"
}

LLM recommendation is informational and validated. Safety severity and activation use documented thresholds and evidence.

Step 5 · Final STATIC API response to application
{
  "routeId":"R-1001", "assessmentId":"A-20261016-001",
  "status":"COMPLETE_WITH_COVERAGE_FLAGS",
  "riskScore":82, "riskLevel":"HIGH",
  "jrmPolyline":"<enriched-polyline>",
  "riskSegments":[{"segmentId":"S-001","type":"SHARP_CURVE",
    "severity":"HIGH","advisory":"Take extra care in wet conditions."}],
  "nearbyLandmarks":[],
  "coverage":{"weather":"AVAILABLE","traffic":"STALE","accidents":"UNAVAILABLE"},
  "dataAsOf":"2026-10-16T00:00:00Z"
}

Do not silently convert unavailable traffic/accident data to “low risk.” Surface coverage explicitly.

Step 6 · Dynamic GPS → queue → cached evaluation → final alert
IN: {"journeyId":"J-1001","lat":12.9716,"lon":77.5946,
     "speedKmph":65,"heading":120,"capturedAt":"2026-10-16T02:30:00Z"}

PATH: MQTT/HTTPS → authentication → event queue → journey worker
      → route/map match → upcoming risk + Redis cached context
      → deterministic alert rules → mobile/voice delivery

OUT: {"journeyId":"J-1001","alerts":[{
  "alertId":"AL-101","riskType":"SHARP_CURVE","severity":"HIGH",
  "distanceMeters":450,"channel":["MOBILE","VOICE_BOX"],
  "message":"Sharp curve ahead. Slow down safely.",
  "expiresAt":"2026-10-16T02:31:00Z"
}]}

Implement idempotency, minimum GPS quality, direction checks, cooldown, retries and device acknowledgement.

08 / Team handoff

Procurement and implementation readiness

Evaluate each external integration

  • Coverage of Indian highways and actual operating corridors
  • Data quality, positional resolution and freshness
  • API response semantics, per-call elements and rate limits
  • Commercial rights, caching / storage / redistribution restrictions
  • Free tier eligibility and paid overage / minimum commit
  • Latency, SLA, outages, regional support and fallback
  • Security, key rotation, data sharing and privacy
  • Observed cache hit rates and cost per real journey

Implementation safeguards

  • Adapter interface per provider; structured validation
  • Backoff, circuit breakers, caching and freshness TTLs
  • PostGIS spatial indexes and route risk versioning
  • Queues only where asynchronous isolation is valuable
  • Vehicle authentication and tenant isolation
  • LLM explanations validated against factual risk events
  • Deterministic, testable safety alert policy
  • Telemetry, API spending budgets and alert quality metrics
This handbook is an evaluation reference, not a signed architecture approval, price guarantee or procurement commitment. Validate provider terms and costs before contracting.
